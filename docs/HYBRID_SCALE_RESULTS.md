# GB10：热工作进程与批量执行分规模实测

2026-09-28，两个实验分支隔离测试，未修改正式部署；代码与脱敏结果随对应实验分支发布，不合并 main。三项任务固定为 revenue 摘要、异常前三例、region 分组 revenue 求和前三组。每条路径先完整预热一次，再正逆序交错测五次，取端到端墙钟中位数；数值结果容差 1e-9 内一致，全量行数一致，源文件未变化，结束无活动会话或缓存帧。

单位秒。倍率 = 同表全 CPU 耗时 / 对应 GPU 路径耗时；小于 1 表示比 CPU 慢。

全 CPU 即未启用 GPU 加速的基线，基准倍率为 1×。新增 CPU 速率单位为万行/秒，按原始未舍入时间计算：数据集行数 ÷ 完成三项分析的总耗时。它是任务吞吐量，不是磁盘读取速度；热工作三个请求仍只以数据集行数 N 为分子，不将三次分析写成 3N 行吞吐量。

## 补测：普通 CPU 独立进程基线

“普通 CPU”不使用 GPU、不复用工作进程、不批量执行；每轮三项分析各新建一个进程，包含三次启动/导入/读取/计算/退出。先做一轮系统缓存预热，但每次分析依然新建进程，因此不是热工作进程。五次重复取中位数，所有输出与 CPU 批量路径、全量行数一致，源文件未变化。

补测发生在上述实验之后，同一设备、文件、查询及 Python 环境，模型保持运行，文件缓存未清；不是七条路径同时交错测试。下面保留上述热工作/批量原值，单位秒。

## 结论与口径

- 2 万、10 万行全 CPU 最快；100 万行混合在两种方向中均最快。相对原生 GPU，混合耗时分别下降约 22.2%（热工作）、18.7%（批量）。这是真实中等规模正例，不代表所有查询和格式。
- 500 万混合仅领先原生约 3.7%/0.6%，不满足 10% 的总成本安全余量，不能据此强制混合。2000 万及以上原生 GPU 更快。
- 亿级三项任务，批量相对热工作耗时下降约 34.1%（CPU）、40.4%（原生 GPU）、43.1%（混合）。这是一次加载和批内统计共享的架构收益，不是 GPU 算力倍率。
- 100 万批量另做五次完整校准并实际调用 auto，选择 CPU 加载＋GPU 计算且结果一致；该额外验证的中位数为 CPU 0.04357、原生 0.04623、混合 0.03770 秒，不替换上表固定轮次数据。
- 100 万热工作三个查询也分别完成五次校准，实际 auto 均选择混合且结果一致。两种方向的中等规模正例均通过了实际路由验证，而不仅是手工挑选最快数字。校准只留在实验目录，没有写入正式配置。
- worker 启动另计：热工作 0.628–0.658 秒，批量 0.630–0.668 秒。每路径的首次完整查询也作为预热单列保留在原始日志中，未计入上表。上表不是独立进程或冷启动成绩。
- 各规模来自同一真实 TLC 数据的前 N 行，无过滤、无复制扩充；子集流式写成两列 Snappy Parquet。全年文件使用既有完整 Parquet，子集的分布、行组布局和编码与完整文件可能不同，因此不能将行数视为唯一性能变量。
- 模型保持运行，未清操作系统文件缓存；不含 LLM 推理和原始 CSV 转 Parquet 的离线准备时间。没有触发内存拒绝，不等于已测得峰值内存。
- 全部实验后模型真实推理返回 OK，既有服务正常；原始材料和隔离测试结果保留，没有删除用户文件。
- 本次比较是强制三路径基准，不把每行最短路径写成已经部署的自动选择；只有额外校准/实际调用通过的任务可以作自动路由证据。
