# 公开数据修复与回归记录

日期：2026-09-28。覆盖 `codex/hybrid-warm-worker` 与 `codex/hybrid-batch`。

## 本轮结果

四套 UCI 公开数据、20 个场景，CPU、原生 GPU、混合请求各五轮，共 300 组计时、900 次分析，全部与 CPU 基准一致。自动执行另行校验，不计入这 300 组。两分支另通过完整 Excel 三步流程，以及 2 万、100 万、113,500,327 行的六个规模场景（90 组计时）。

这里的目标是正确且合算地选择引擎。小数据、55 列摘要并未因为修复而变成 GPU 优势场景；实际校准选择了 CPU。1.135 亿行批量计算中，原生 GPU 为 CPU 的 2.63 倍速度，混合路径为 2.14 倍，原生 GPU 仍更合算。

## 五项工作

1. **CUDA 环境**：系统已有 CUDA 13.0 头文件。为隔离实验设置正确的 `CUDA_PATH` 后，CuPy 内核能够编译执行，修复了之前的头文件查找失败。没有安装或升级正式环境的软件。实测环境为 Python 3.11、cuDF 25.10.0、CuPy 14.2.0；头文件配置参见 [CuPy 官方安装说明](https://docs.cupy.dev/en/stable/install.html)。
2. **含空值 Pearson**：GPU 使用 float64 和成对有限值语义，处理 null、NaN、无穷值、常量和有效配对不足两个的情况。缺失值没有填零，也没有对原始表整体删行。仅在确认所有字段有效值位置完全一致后，才共享矩阵计算；其他情况逐对计算并去均值。仅最终相关矩阵传回 CPU 组织结果。
3. **文件读取及引擎真实性**：CSV 以最多 64 KiB 内容识别逗号、分号、Tab、竖线，识别结果按文件身份缓存，文件变化失效；旧 CSV 转 Parquet 缓存不再复用。XLSX 在 CPU 读取后转 Arrow/cuDF，记录真实 CPU 读取和 GPU 转换。JSON、旧 XLS 保守使用 CPU。XLSX 不可表示的数据类型仍允许明确的 CPU 回退。
4. **选择与保护**：先检查已知格式、字段和算子限制，避免已知失败路径先读 GPU 再读 CPU。混合加载不适用时，仍可在经过验证的 CPU/原生 GPU 两个候选之间校准。保留 24 小时、文件/列/查询/冷热状态/设备/软件绑定以及 5%/10%/10% 收益门槛；新增实现版本失效标识。标记为 warm 的请求不读取或写入冷请求成本样本。Excel 在解压尺寸及实际解码后分别准入；相关性计算另外预留临时数组空间；内存拒绝不会通过 CPU 重试绕过。
5. **回归及慢点优化**：复测四套公开数据、两种执行方式及亿级材料，补充可复现脚本、原始样本和自动选择证据。缓存 CSV 分隔符识别，优化共同空值位置的相关性计算；批量模式保持一次读取、一次转换和批内统计复用。

两分支都使用同一套读取、相关性和校准修复。热工作分支按每次请求选择路径；批量分支按完整步骤与列并集选择，批内共享数据。批量加载耗时额外保留未舍入值，供校准使用。

CPU 基准与 GPU 使用同一执行方式：热工作 CPU 对热工作 GPU、批量 CPU 对批量 GPU。**不是与三次新建 CPU 进程相比。** C=CPU，G=GPU 原生读取并计算，H=CPU 加载后 GPU 计算。自动选择列来自一次执行核验，不是五轮性能中位数。混合请求的 G/C 组合按三个步骤列出，包含 CPU 的组合不能当作纯 GPU 加速成绩。

## 修复前后

以下是此前已保存记录与本轮中位数对照，单位秒。旧版这两个相关性场景的 GPU 请求均包含相关性步骤回退 CPU；新版三步都能在 GPU 完成。它们不是同期配对实验，几个百分点的差别不足以证明稳定收益。

| 场景 | 旧 GPU 请求，含 CPU 回退 | 新原生 GPU 全流程 | 旧混合请求，含 CPU 回退 | 新混合 GPU 全流程 |
|---|---:|---:|---:|---:|
| 热工作 / 森林 / 10 列＋相关性 | 0.225106 | 0.153286 | 0.207237 | 0.136656 |
| 热工作 / 用电 / 数值＋含空值相关性 | 0.246147 | 0.237899 | 0.213744 | 0.205917 |
| 批量 / 森林 / 10 列＋相关性 | 0.191396 | 0.120204 | 0.185117 | 0.115297 |
| 批量 / 用电 / 数值＋含空值相关性 | 0.171795 | 0.165055 | 0.158704 | 0.152062 |

森林相关性工作流改善明显。家庭用电的主要成果是保持空值语义并真正完成 GPU 计算，整个工作流没有出现数量级提速。分号 CSV 原先因选列失败而无法执行，现在两引擎均读通；Excel 原先请求 GPU 时读取器仍返回 pandas，现在数值投影实际返回 cuDF。

## 完整 Excel 验证

直接读取 541,909 行的原始工作簿，执行数量/单价摘要、单价异常值、客户数量分组，与经过全量往返核验的 Parquet 的 CPU 结果比较。下面是单次集成测试，主要验证正确性和读取/转换次数，不据此声称稳定的 CPU/GPU 加速比。

| 方式 | 行数 | CPU 读取次数 | GPU 转换次数 | 单次秒数 | 三步结果 |
|---|---:|---:|---:|---:|---|
| 热工作 | 541,909 | 3 | 3 | 35.550 | GPU/GPU/GPU，与 CPU 参考一致 |
| 批量 | 541,909 | 1 | 1 | 12.287 | GPU/GPU/GPU，与 CPU 参考一致 |

输入身份保持不变；实验结束时活动数据会话与数据帧缓存均为零。驻留模型的最终健康检查返回 `OK`。两分支各七项契约测试在真实 GPU 环境通过，覆盖分隔符、空值/无穷值/常量、Excel 桥接、内存拒绝和冷热成本隔离；本地 Arrow/校准测试 18 项、批量契约 8 项及相关既有回归也通过。

## 复现

在各自分支的仓库根目录，使用包含 cuDF、CuPy、PyArrow、pandas、openpyxl 的解释器。先确保 CuPy 可以编译简单运算；本机测试使用系统已有 SBSA CUDA 头文件目录配置 `CUDA_PATH`，其他机器应按自己的 CUDA 安装选择目录。

数据目录须包含来源记录对应的 `wine.parquet`、`forest.parquet`、`power.parquet`、`retail.parquet`、`wine-comma.csv`、`wine-original.csv`，Excel 验证另需 `retail-original.xlsx`。所有源 ZIP 和数据留在实验数据目录，不加入源码仓库。

热工作分支：
```sh
python benchmark/public_data_regression.py --dataset-root /absolute/uci-data \
  --mode warm --repeats 5 --profile hybrid-profiles/public-warm.json
python benchmark/format_bridge_smoke.py --dataset-root /absolute/uci-data --mode warm
```

批量分支：
```sh
python benchmark/public_data_regression.py --dataset-root /absolute/uci-data \
  --mode batch --repeats 5 --profile hybrid-profiles/public-batch.json
python benchmark/format_bridge_smoke.py --dataset-root /absolute/uci-data --mode batch
```

真实 GPU 边界测试：
```sh
export GDA_EXCEL_FIXTURE=/absolute/uci-data/retail-original.xlsx
python skills/cudf-analytics/scripts/diversity_regression_test.py --gpu
```

校准只在明确评测时建立。正常请求可设置 `GPU_ANALYSIS_HYBRID_PROFILE` 指向本机生成的对应文件；文件、字段、查询或环境不匹配时不复用。不要把这些设备相关校准文件提交到 Git。

## 证据与限制

- [热工作完整样本](hybrid-evidence/public-repair-warm.jsonl)、[批量完整样本](hybrid-evidence/public-repair-batch.jsonl)、[修复前摘要](hybrid-evidence/public-repair-before.jsonl)。
- [分规模完整样本](hybrid-evidence/public-repair-scale.jsonl)、[完整 Excel 验证](hybrid-evidence/public-repair-excel.jsonl)。
- 内存准入是保守估算，本轮未测峰值内存；统一内存也不代表转换零拷贝。
- 不同空值位置的 Pearson 仍可能需要逐对计算；宽表摘要和小文件继续可能由 CPU 获胜。
- 当前混合 Parquet 加载器仍限平坦数值/布尔列；字符串、时间戳可以通过原生 GPU 候选参与比较。CSV 支持读取修复，但没有新增 CSV 混合桥；旧 XLS、JSON 当前使用 CPU。
- 精确查询校准尚不泛化到任意未见数据和查询；无匹配校准时沿用保守默认策略，不能保证每次都选到最快者。
- Excel 的投影列须可转换为 Arrow/cuDF；异质对象列等不支持情形如实回退。完整 Excel 测试验证的是文中指定的数值分析，不代表任意 Excel 内容都能 GPU 加速。
