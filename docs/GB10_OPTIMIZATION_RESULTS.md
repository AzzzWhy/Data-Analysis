# GB10 精确分析与报表队列优化验收（2026-09-28）

## 结论与测试边界

本轮减少启动、读取、重复计算和路由开销，保留精确结果、内存保护和 GPU 跨进程计算许可。已测的三档 TLC 数值 Parquet 中，自动路由选择最快引擎类别；相对显式最快路径仍有路由管理开销，不能称为每次都绝对最快，更不能推广到所有数据。

机器为 GB10；输入为 20,000、1,000,000、113,500,327 行的 `region`、`revenue` 两列。统一执行摘要、IQR 异常检测和区域收入求和，不抽样、不近似。四份报表分别取 top-K 1、2、3、4，均输出独立 Markdown 和 JSON。五轮交错测量取中位数，结果与独立 CPU 计算逐项按绝对/相对容差 `1e-9` 核对。源文件保持不变。

单次工作流的旧实现来自修改前的 GB10 `c6b33f0`，运行代码与本地修改前 `3d6a7f8` 一致。四报表旧队列记录来自同日上一轮测量：旧计划接口不支持强制原生 GPU，所以“旧最快”指当时**已测、可用的实现**，不是旧算法理论最优。新单工作流 before/after 是本轮同环境重新交错测量；四报表旧记录并非本轮重新交错测量。

保持操作系统文件缓存和本地模型服务原状。不计 LLM 请求、校准生成时间；冷启动仅指分析进程新建，不指清空文件缓存。常驻跨提交只复用进程，每次重新读取并在事务结束释放帧，不跨清单缓存数据。

## 实际改动

- 固定报表队列默认使用独立于 Agent 对话的可复用分析进程；省去中转任务进程。显式纯 CPU 不兼容数据组仍可多进程并行，GPU 风险组串行并保留跨进程许可。
- 相邻同文件、同配置计划合成有界事务，投影列取并集、读取一次；摘要、异常值、分组结果在同一事务精确复用，top-K 使用最大结果裁剪。复用步骤明确标为 `rows_scanned=0`、`result_reused=true`，不虚构重复扫描。
- Parquet 用元数据真实行数，不按 CSV 换行估行；热路由和内存准入考虑投影列解码大小，避免压缩后小文件被误当小数据。
- 摘要避免重复 `dropna`；机器环境指纹缓存并按相关环境变量变化失效。
- `reports_warm` 按整份共享事务校准，普通单批使用独立的 `batch_warm`/`batch_cold` 口径。校准绑定文件、列、参数、机器、算法版本，24 小时过期；旧版本失效。不存在可跨任意机器无限沿用的最佳阈值。
- 合并读取失败时回退到逐计划，保留可成功任务；分析超时停止 worker。原 `isolated` 模式继续支持包含报告写入的进程级硬超时。

CPU 读取与 GPU 计算目前顺序衔接，并非异步分块流水线；统一内存不等于数据转换无成本。该亿级数据实测原生 GPU 比 CPU→GPU 更快，强制混合没有额外收益。

## 回归与复测

GB10 显式单元模块验收共运行 105 项：104 通过、1 项跳过（需另加 `--gpu` 启用的真实 GPU 多格式桥接测试）。覆盖共享结果、不同 top-K、源文件变更、失败隔离、CPU 子进程复用、并行、自动路由、超时与退出清理。没有声称全仓库通配发现都通过。

部署目录重复验收得到同样结果。额外启用真实 Excel GPU 桥接时，先发现需要指定现有 Online Retail 测试文件，随后发现基础 RAPIDS 环境缺少可选依赖 `openpyxl`。仅在临时测试目录安装依赖、通过 `PYTHONPATH` 启用后，7 项多格式回归全部通过，包含真实 Excel→GPU 与读取前内存拒绝；未修改基础环境或模型服务。普通部署要读取 Excel 仍需安装该可选依赖，不能将临时测试成功说成基础环境已具备依赖。

部署后的三档四报表自动队列均成功，每档一个共享事务；单轮冷调用组级耗时约 0.202、0.240、2.730 秒，不替代前述五轮统计。旧独立模式及 Agent 热会话联测也通过：两 CPU 子进程时间重叠、GPU 作业串行、热会话实际等待共享 GPU 许可约 1.215 秒，数值一致、原始文件未变，结束无活动会话或分析进程残留。[部署联测记录](hybrid-evidence/optimized-gb10-20260928/deployment-live.json)。
