# 常驻与批量执行：GB10 实验记录

本轮在 `1eb53f7` 的基础上开发，未提交或推送 GitHub。实验位于 GB10 临时目录 `/tmp/gda-fast-check.2o4OxJ`，未替换正式部署或修改已有模型配置。

## 已实现

1. 普通分析不默认额外执行 CPU 对照。`SKILL_SHOW_SPEEDUP=1` 保留评测模式；该模式使用独立进程，避免冷热上下文的不公平对比。脚本演示显式开启评测。
2. 单次分析复用工作进程及 CUDA 上下文，但不缓存该次结果或数据帧；进程失败可降级，超时停止后可重启。
3. 新增 `analyze_batch`：最多八项独立分析，所需列取并集、加载一次、共享精确统计量、自动释放会话。失败中止并报告已完成步骤；不借用模型已有的同文件会话。
4. 区分初始化、加载、计算、工作进程通信总时间。首次工作进程启动不能从端到端时间中消失。
5. 统一工具选择提示，去掉旧规则中“必须用单次分析工具”的冲突。未测量 CPU/GPU 对照时，工具明确返回无对照并要求模型不编造倍率。

## 实测

硬件 NVIDIA GB10，cuDF 25.10.00，pandas 2.3.3；模型 `qwen3.6-35b-a3b-fp8`。

每个案例执行完全相同的三项分析：revenue 摘要、revenue 异常检测（前三个示例）、region 的 revenue 总和前三组。每模式两次、交错执行，表中为中位墙钟耗时。

| 案例 | 每项独立进程 | 热工作进程，仍读三次 | 批量，加载一次 |
|---|---:|---:|---:|
| 2 万行，合成数据，CPU | 0.595 秒 | 0.00775 秒 | 0.00463 秒 |
| 500 万行，现有数据，GPU | 5.008 秒 | 0.860 秒 | 0.243 秒 |
| 2000 万行，现有数据，GPU | 7.812 秒 | 3.035 秒 | 内存保护拒绝 |

- 500 万行：热工作进程约快 5.82 倍；批量约快 20.64 倍，相对于同一 GPU 的独立进程执行方式，不是 GPU 对 CPU 的倍率。
- 2000 万行：热工作进程约快 2.57 倍。批量所用原有保守保护估计需要 12.5 GB，探测仅剩 11.5 GB，拒绝加载；没有降低阈值或停止模型。不能给该案例编造批量耗时。
- 工作进程首启和 GPU 探测耗时另测为 0.636 秒；热模式表格不包括它。实际首次回答仍承担这笔成本。
- 小数据的巨大热态比值主要来自省掉进程启动，绝不是小数据 GPU 算法加速；此案例使用 CPU。
- 已完成各模式的数值结果一致性检查，容差 1e-9。500 万行批量异常检测明确复用 revenue 的统计量。
- 不含模型推理、没有清空系统页缓存，重复次数仅两次；这是工程验证，不是普遍性能上限或竞赛最终基准。

## 测试与真实模型

- 本机新增执行测试十三项、交互复用五项、优化九项、统计复用十二项、分组覆盖和工具契约通过。
- 本机分析冒烟通过；本机无 cuDF，GPU 部分不能在此验证。
- GB10 强制 GPU 冒烟通过。
- GB10 新增执行测试十三项、外部 skill/MCP 测试三十三项通过。
- GB10 本地 Qwen 在一条普通需求中自主调用一次 `analyze_batch`，完成摘要、异常检测、分组汇总，核对真实工具返回，最终答案正确说明 CPU 执行，没有编造 GPU 加速倍率。

模型侧最初确实未选批量工具；修复冲突提示后选择批量。另一次答案套用了旧加速模板，虚构了倍率；增加“没有比较对象就不得给基线或倍率”的规则和工具证据说明后，同一需求重测通过。这是一条验证过的案例，不能保证所有模型或任意任务都遵循规则。

## 收尾与剩余工作

输入文件身份信息前后未变化，基准中的会话和热缓存均为零；实验后模型服务仍正常。临时目录保留供复查，不是生产部署。

Parquet 缓存已有但仍为显式启用，本轮没有实现自动缓存策略或过滤下推；DuckDB 多线程 CPU 后端、投影感知的可靠内存预算、模型端到端分段基准也仍待开发。后续应增加重复次数与缓存状态控制，再形成竞赛性能结论。
