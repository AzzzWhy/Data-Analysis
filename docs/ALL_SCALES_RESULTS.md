# 七档规模：当前实现是否最快（GB10，2026-09-29）

结论：**不是每档、每种执行状态都最快。** 当前版在同轮交错对照中，对 500 万至 1.135 亿行的单次三项分析有明显收益；100 万行收益很小；2 万与 10 万行应使用 CPU，当前与上一版的毫秒级差异不能概括为稳定加速。尤其在每次新建队列进程的四报表任务中，5000 万及 1.135 亿行的显式 CPU 读取＋GPU 计算快于当前自动路由。七档热态记录逐项核对了独立 CPU 计算；冷启动记录核对四种路径相互一致。两套记录均确认原始文件身份未变，热态结束后没有活动数据会话。

## 同一任务、同一数据的单次工作流

数据为纽约市 TLC 全量视图及其同源前缀，均为 `region`、`revenue` 两列 Parquet；分别执行精确摘要、IQR 异常值和区域汇总。上一版和当前版各自强制 CPU、原生 GPU、CPU 读取＋GPU 计算，交错五轮取中位数。工作进程已启动，但每次重新读取数据；不含模型推理。表中“上一版最快”和“当前最快”均是三个显式路径的最小中位数，不是自动路由耗时。

| 行数 | 上一版最快（秒） | 当前最快（秒） | 当前最快路径 | 上一版/当前 |
| ---: | ---: | ---: | --- | ---: |
| 20,000 | 0.00635 | 0.00747 | CPU | 0.85×* |
| 100,000 | 0.00933 | 0.01039 | CPU | 0.90× |
| 1,000,000 | 0.03742 | 0.03646 | CPU 读取＋GPU | 1.03×* |
| 5,000,000 | 0.10969 | 0.08337 | CPU 读取＋GPU | 1.32× |
| 20,000,000 | 0.31002 | 0.20335 | 原生 GPU | 1.52× |
| 50,000,000 | 0.67836 | 0.41872 | 原生 GPU | 1.62× |
| 113,500,327 | 1.43239 | 0.85713 | 原生 GPU | 1.67× |

`*` 小幅差异不作稳定优劣结论。2 万行追加的 20 轮复测甚至反转为上一版 0.01145、当前 0.00683 秒，说明短任务受运行环境影响明显。10 万行 20 轮为上一版 0.00893、当前 0.00966 秒；关闭新统计算法后当前为 0.00914 秒，接近上一版。这提示新入口的守卫检查有小额成本，但不足以据此认定固定的硬件极限。100 万行约 3% 的差距同样需要更多独立重复才能声称稳定收益。

## 四份报表：热队列与完整冷启动

每档同源数据产生四份不同 top-K 的完整 JSON/Markdown 报表。热队列复用已经启动的分析进程；“完整冷启动”则每个样本重新启动并退出**队列 CLI 及其 worker**。操作系统文件缓存保留，因此“冷”不代表清空文件缓存。表格均为五轮中位数，单位秒。热队列的“最优显式”取 CPU、原生 GPU、混合三路的最小值；自动路径仍会做决策，通常稍慢。

| 行数 | 热队列最优显式 | 热队列自动 | 冷 CLI 最优显式（路径） | 冷 CLI 自动 | 自动冷路径 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 20,000 | 0.026 | 0.023* | 0.424（CPU） | 0.425 | CPU |
| 100,000 | 0.026 | 0.028 | 0.429（CPU） | 0.441 | CPU |
| 1,000,000 | 0.051 | 0.053 | 0.450（CPU） | 0.461 | CPU |
| 5,000,000 | 0.099 | 0.101 | 0.598（CPU） | 0.618 | CPU |
| 20,000,000 | 0.221 | 0.221 | 1.089（CPU） | 1.125 | CPU |
| 50,000,000 | 0.432 | 0.434 | **1.827（CPU 读取＋GPU）** | 2.187 | 原生 GPU |
| 113,500,327 | 0.865 | 0.866 | **2.443（CPU 读取＋GPU）** | 2.605 | 原生 GPU |

`*` 2 万行热队列的五轮自动值偶然低于显式 CPU；20 轮复测则为显式 CPU 0.02338、自动 0.02512 秒，不应把该差异解释为自动路由能超越它选择的 CPU 路径。

5000 万行冷 CLI 自动比本轮最优慢 **19.7%**，1.135 亿行慢 **6.6%**。两档五轮样本区间均分离，不是仅由某一次离群值造成。自动计划携带的校准为 `reports_warm`；新进程请求的实际上下文为 `reports_cold`，决策记录显示“无匹配校准”，然后按 Parquet 解码规模启发式选了原生 GPU。热态和冷态的最优路径不同，不能复用热态阈值来声称全局最快。若目标是在所有已测场景自动取得显式最优，仍需建立并验证冷报表校准与冷态路由规则。

完整冷 CLI 用时高于[上一轮报告](FINAL_ROUND_RESULTS.md)中的“冷自动”用时，因为后者在已启动的基准主进程内调用队列库，包含 worker 启停但**不包含队列 CLI 进程启动**；两种数值不可直接计算加速比。校准生成时间、模型推理和网络请求都不在上述计时中。范围也仅限这份双列数值 Parquet 与这组三项算子，不能推论任意宽表、字符串列或其他数据源。
