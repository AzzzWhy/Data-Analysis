# 分支二：CPU 加载＋GPU 计算，热工作进程

- 分支：`codex/hybrid-warm-worker`。
- 起点：GitHub `main` 的 `59b5229ba9d6a5fbe4eefeabaf2de05cc627a3be`，与另外两个分支相同。
- 状态：**开发方案，未实现混合加载后端，未测得混合执行加速倍率**。main 已有常驻工作进程和 oneshot 接口，本分支是在这个基础上规划 CPU 加载路径，不是声称现有 worker 已混合执行。

## 目标与边界

CPU 读取所需列 → 转换为 GPU 数据帧 → GPU 精确计算，在跨请求复用的工作进程中执行。解释器、依赖和 CUDA 上下文初始化一次，连续请求复用；**每个独立请求仍重新读取和转换数据，结束释放该请求的帧**。

基础方案不缓存数据帧、统计或结果，也不把多个请求合成一次批量加载。这样可以把“热进程收益”与“批量/数据常驻收益”分开验证。以后若增加数据缓存，应另外标记并报告命中，不能偷偷并入热进程成绩。

## 待实现任务

1. 在 `gpu_analytics.py` 增加 CPU/PyArrow Parquet 投影读取与 Arrow→cuDF 转换选项；在 `gpu_session.py` 的 oneshot 请求中明确传递读取/计算选择，保留主干正常 CPU/GPU 路径。
2. 与 `agent/skills.py` 现有持久 worker 对接，完整记录请求墙钟时间；第一请求包括 worker 启动、导入及 CUDA 延迟初始化。后续请求分别计 CPU 读取、转换、GPU 计算和通信。
3. 复用引擎/上下文，但在 `finally` 释放每次分析帧和转换中间态；避免 CPU-only 请求仅为清理而启动 CUDA。内存池保留与真实活动帧需分别报告。
4. 保留请求串行化、超时终止、故障重启、stderr 排空及有界错误信息。转换失败、GPU 错误应清理后明确回退；传输失败的独立进程重试必须标出模式变化和全部实际耗时。
5. 自动路由使用常驻条件下的估计，不把冷启动估计套到已热的请求，也不把未测过的初始化当作零。候选路径比较 CPU 读取＋转换＋GPU 计算与同稳态 CPU/原生 GPU 总成本。
6. 测试连续请求、CPU/GPU 切换、文件变更、不支持类型、无 GPU、内存不足、转换异常、超时、worker 重启及关闭。保留主干内存保护，不停止模型、不自动清系统缓存。

## 基准与验收

全 CPU、原生 GPU、CPU 加载＋GPU 计算均在同种常驻执行条件下测量。相同文件、列、查询，每次请求重新读取，不复用数据帧；结果缓存禁用。首先测首启完整耗时，再明确预热，至少五次正逆序交错测稳态中位数及波动。

热态表格不能隐藏首次 CUDA 操作或恢复后的重新初始化。分开列出 worker 启动、GPU 初始化、CPU 读取、转换、计算、通信、完整请求耗时；GPU 异步阶段同步后计时。文件缓存状态与模型负载一并记录，不能把操作系统缓存命中写成计算加速。

共同材料覆盖小样本、500 万、2000 万及 TLC 全年 113,500,327 行。检查全量行数、数值容差 1e-9、类型/空值、异常边界及分组覆盖；每请求结束无活动帧、无结果或数据缓存，终止 worker 后资源可回收。

已有上亿行主干常驻三项查询：CPU 6.093 秒、原生 GPU 2.881 秒。这只作为同口径基线，**不能承诺加入 CPU 加载就更快**。发布前提供完整首启/稳态对照，证明自动选择不会因额外转换普遍倒退。

## 不在本分支范围

批量加载一次、跨请求帧缓存、共享统计、异步双缓冲和多 worker 并发。独立单次方向在 `codex/hybrid-single-process`；批量方向在 `codex/hybrid-batch`。

共同规则与源数据限制见 [三分支总览](HYBRID_BRANCHES.md)，已有实验见 [基线报告](POST_CACHE_AND_PUBLIC_DATA_RESULTS.md)。完成实现与验证前不合入 main，也不替换 GB10 正式部署。
