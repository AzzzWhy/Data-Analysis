# 分支一：CPU 加载＋GPU 计算，单进程单次执行

- 分支：`codex/hybrid-single-process`。
- 起点：GitHub `main` 的 `59b5229ba9d6a5fbe4eefeabaf2de05cc627a3be`，与另外两个分支相同。
- 状态：**开发方案，未实现混合加载后端，未测得混合执行加速倍率**。当前继承 main 已验证的 CPU、GPU 原生读取、常驻和批量功能，不代表此分支已改变执行默认值。

## 目标与边界

当 CPU 解码更合算、GPU 计算收益足够大时，在**一次分析进程内**完成 CPU 读取 → GPU 数据帧转换 → GPU 精确计算 → 返回结果 → 释放资源并退出。这里“单进程”指分析后端无需另设 CPU worker 和 GPU worker，不要求模型/TUI 与后端处于同一进程。

重点检验冷启动下的端到端收益。不同 CLI 调用不得复用 CUDA 上下文、数据帧、统计或结果缓存；不靠热工作进程、不靠多任务批量来隐藏启动成本。单次允许 CPU 读取库内部使用线程，但不添加进程池；记录其线程配置。

## 待实现任务

1. 在 `skills/cudf-analytics/scripts/gpu_analytics.py` 的加载层增加可选 CPU/PyArrow Parquet 投影读取，按单次操作提取必需列；直接转换为 cuDF，避免不必要 pandas 中间帧。保持原生 CPU/GPU 路径。
2. 分离读取后端与计算后端：明确返回 `load_engine`、`compute_engine`、转换耗时、实际引擎与降级原因。现有 `engine=cudf` 仅说明计算，不足以证明加载路径。
3. 在同一进程控制初始化、加载、转换和计算生命周期；必要 GPU 初始化仍存在，不能声称“GPU 初始化移到 CPU”。GPU 阶段同步后计时，释放放入 `finally`。
4. 混合路径也需预先预算 CPU 帧、GPU 帧、转换中间态及计算工作区，遵守已有内存保护。不能以统一内存为理由跳过预算或宣称零拷贝。
5. 显式强制路径用于评测；自动选择仅在可靠成本估计支持时启用。选择比较的是包含冷启动的总时间，收益不足用 CPU 或原生 GPU，不重复运行完整任务来选路。
6. 为加载、类型/空值一致性、转换失败、无 GPU、内存不足及资源清理增加测试。最初支持 Parquet；CSV 后续单独评测，不混入格式变化收益。

## 基准与验收

每个查询分别启动一次新分析进程，比较全 CPU、原生 GPU、CPU 加载＋GPU 计算。相同文件、列、查询、结果范围；至少五次交错测量，报告中位数和波动。测多查询总和时必须都启动相同数量的进程；不得拿本分支三次加载与批量一次加载当硬件对照。

单独记录：进程启动/退出、引擎初始化、CPU 读取、转换、GPU 计算、结果序列化和端到端时间。进程冷启动不等于文件缓存冷态；缓存状态必须说明，不能自行清系统缓存或停止模型。

共同材料覆盖小样本、500 万、2000 万以及 TLC 全年 113,500,327 行。保留原始输入、全量扫描行数，数值容差原则为 1e-9，另外核对类型、空值、异常边界和分组覆盖。结果有差异、OOM 或偷偷回退 CPU 时不得宣称 GPU 加速。

发布前必须给出至少一个公平且可复现的混合收益案例，并证明不合算时保守路由。当前主干上亿行独立进程 CPU 6.838 秒、原生 GPU 7.140 秒是三项分析总和，只是问题基线，**不意味着混合一定更快**。

## 不在本分支范围

跨请求热进程、GPU 数据常驻缓存、批量步骤共享统计、异步流水线或 CPU/GPU 同时重复算同一任务。另两个方向分别位于 `codex/hybrid-warm-worker`、`codex/hybrid-batch`。

共同规则与源数据限制见 [三分支总览](HYBRID_BRANCHES.md)，已有实验见 [基线报告](POST_CACHE_AND_PUBLIC_DATA_RESULTS.md)。完成实现与验证前不合入 main，也不替换 GB10 正式部署。
