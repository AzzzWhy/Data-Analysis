# 分支三：CPU 加载＋GPU 计算，批量执行

- 分支：`codex/hybrid-batch`。
- 起点：GitHub `main` 的 `59b5229ba9d6a5fbe4eefeabaf2de05cc627a3be`，与另外两个分支相同。
- 状态：**开发方案，未实现混合加载后端，未测得混合执行加速倍率**。main 已有 `analyze_batch` 的 GPU 原生读取与全 CPU 批量执行，本分支规划为它增加第三条混合路径。

## 目标与边界

一次请求中，对同一文件执行 1–8 项已确定的独立分析：收集所有步骤所需列的并集 → CPU 投影读取一次 → 转换为 GPU 数据帧一次 → 按序执行全部步骤 → 共享可复用的精确统计 → 自动关闭并释放帧。

复用主干工作进程，批内共享数据，批间不新增帧或结果缓存。不能把依赖前一步结果才能确定参数的自适应分析强行合成静态批次；这类任务仍使用现有会话流程。批量收益与 GPU/CPU 硬件收益要分开报告。

## 待实现任务

1. 在 `gpu_analytics.py` 增加 CPU/PyArrow Parquet 投影读取及 Arrow→cuDF 转换。在 `gpu_session.py` 的批量专用加载入口传入读取后端，不改变已有会话生命周期与正常读取路径。
2. 根据全部步骤取所需列并集；CPU 读取一次、GPU 转换一次，记录次数与投影列。任一步需要所有列时必须据实预算，不能偷偷漏列或只取前若干行。
3. 保留精确分位数和有效计数复用，统计只能在同一有效帧上复用；不会复用不兼容的列、方法或变更后的数据。不以近似统计或抽样换取倍率。
4. 预检查读入、转换中间态、驻留帧及最重步骤的峰值内存。CPU/GPU 共用 RAM 不等于无需转换或只计算一份内存。批量保留限制，不降低保护阈值、不停止模型、不自动清文件缓存。
5. 成本决策考虑完整步骤集合、读取与转换一次、GPU 计算及统计复用；分别比较同样批量优化的 CPU、GPU 原生和混合路径，不能只拿未经优化 CPU 作对照。
6. 报告批次端到端时间、初始化、CPU 读取、转换、每步计算、统计复用、真实引擎和降级。GPU 异步阶段同步后计时，显式区分首启与稳态。
7. 确保任意步骤错误、转换异常、超时或取消都关闭本批独占会话；不借用或关闭用户已有同文件会话。明确失败步骤及已完成结果，避免悄悄重复整个批次或伪装所有步骤均在 GPU。
8. 增加投影并集、一次读取/转换、统计复用、逐步正确性、异常清理、同文件会话冲突、引擎降级及超限测试。模型提示只引导已知列的独立需求批量，不改变自适应分析语义。

## 基准与验收

全 CPU 批量、GPU 原生批量、混合批量使用同一文件、同列并集、相同步骤及相同复用规则，均只加载一次。至少五次交错测量，分开报告首次含 worker/CUDA 启动的端到端时间与预热稳态中位数、波动。

既测单步请求的额外开销，也测三个步骤的共享收益；记录共享帧字节数、内存峰值、每步真实引擎、读取/转换次数。内存量应实际测量并标出工具口径，不把文件大小当作解码后帧大小。

共同材料覆盖小样本、500 万、2000 万及 TLC 全年 113,500,327 行。全部步骤保留全量行数、数值容差 1e-9、类型/空值与异常边界、分组覆盖一致性。批次结束本批活动会话和帧为零，输入未变，模型仍能正常推理。

已有上亿行主干 CPU 批量 4.008 秒、GPU 原生批量 1.528 秒，GPU 原生批量加载约 0.132 秒；这提示 CPU 加载并不必然合算。**混合路径只有在包含转换成本的完整批量时间更优时才能被选中**。不能把 GPU 独立进程/批量的 4.67 倍标成混合 GPU/CPU 倍率。

## 不在本分支范围

跨文件批处理、跨请求数据缓存、在线流式分位数、近似算法、多 GPU、异步双缓冲或让 CPU/GPU 同时重复整批计算。另两个方向分别位于 `codex/hybrid-single-process`、`codex/hybrid-warm-worker`。

共同规则与源数据限制见 [三分支总览](HYBRID_BRANCHES.md)，已有实验见 [基线报告](POST_CACHE_AND_PUBLIC_DATA_RESULTS.md)。完成实现与验证前不合入 main，也不替换 GB10 正式部署。
